## 1. 流水线设计

### 1.1 `.github/workflows/ci.yml` 全文

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  build:
    name: build
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      # 不写 with.version：pnpm/action-setup@v4 会读根 package.json 的
      # packageManager（pnpm@10.29.3）。version 与 packageManager 不一致时，
      # action 源码直接抛 "Multiple versions of pnpm specified"。
      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node.js 24
        uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Build blog
        run: pnpm --filter blog build

      - name: Verify CSS baseline
        run: pnpm verify

      - name: Upload dist artifact
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: examples/blog/dist
          if-no-files-found: error
```

| 3–6 | 触发：push 到 `main`、所有 `pull_request`（默认 opened/synchronize/reopened） |
| 8–10 | 并发：同 ref 新 run 取消旧 run，避免重复构建 |

| 27–28 | `pnpm/action-setup@v4`：按根 `package.json` 的 `packageManager` 装 pnpm 10.29.3；**必须排在第 2 步**，action 需要 checkout 后的 workspace 才能读到 `packageManager` |

### 1.2 与 PLAN §6.1 的差异（逐条说明）

| PLAN §6.1 原文 | 实际实现 | 原因 |
| --- | --- | --- |
| `pnpm/action-setup@v4` + `with: { version: 10 }` | 只写 `uses: pnpm/action-setup@v4`，不写 `version` | 根 `package.json` 第 5 行 `"packageManager": "pnpm@10.29.3"`。action 源码在 `version` 与 `packageManager` 不一致时直接抛错（见 1.3），写 `version: 10` 必红 |
| 无 `permissions` | `permissions: contents: read` | 最小权限；本流程只需要 checkout 读仓库 |
| 无 `timeout-minutes` | `timeout-minutes: 15` | 防止 install/build 卡死占用 runner（GitHub 默认 360 分钟） |
| `upload-artifact` 只给 name/path | 追加 `if-no-files-found: error` | 构建「成功」但 dist 为空时直接暴露，而不是传一个空 artifact |
| `concurrency` / 触发条件 / Node 24 / `--frozen-lockfile` / `--filter blog` | 与 PLAN 一致 | — |

### 1.3 为什么不能写 `with.version: 10`（证据）

`pnpm/action-setup` 的 `readTargetVersion` 实现（`master` 分支 `src/install-pnpm/run.ts`）在 `version` 与 `packageManager` 版本不一致时抛错，错误原文：

```ts
if (version) {
  if (packageManagerVersion && packageManagerVersion !== version) {
    throw new Error(`Multiple versions of pnpm specified:
    - version ${version} in the GitHub Action config with the key "version"
    - version ${packageManager} in the package.json with the key "packageManager"
  Remove one of these versions to avoid version mismatch errors like ERR_PNPM_BAD_PM_VERSION`)
```

- 来源：<https://github.com/pnpm/action-setup/blob/master/src/install-pnpm/run.ts>（通过 `gh api repos/pnpm/action-setup/contents/src/install-pnpm/run.ts -H "Accept: application/vnd.github.raw"` 取原文后 `Select-String`）
- README 同样写着：`version` 在 `package.json` 声明 `packageManager` 时是 Optional，省略就用 `packageManager` 的值。<https://github.com/pnpm/action-setup#readme>
- 本仓库实测冲突：`version: 10` vs `packageManager: 10.29.3` → `10 !== 10.29.3` → 抛错。省略 `version` 后 action 安装 **10.29.3**，与本地 `pnpm --version` 输出 `10.29.3` 一致。

## 2. `scripts/verify-css.mjs`

### 2.1 读什么

| 输入 | 默认路径 | 覆盖方式 |
| --- | --- | --- |
| baseline 摘要 | `docs/reference/baseline.json`（路径由脚本自身位置推导：`path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..')`，与 cwd 无关） | 环境变量 `BASELINE_PATH`（仅本地调试，CI 不设置） |
| 构建产物 | `examples/blog/dist` | 环境变量 `DIST_DIR`（仅本地调试，CI 不设置） |

从 baseline 只消费 `css.*` 三个字段（`baseline` / `pages` / `fixtures` 不读）：

```json
{ "baseline": { "commit": "...", "version": "...", "generatedAt": "..." },
  "css": { "indexCssBytes": 0, "indexCssGzipBytes": 0, "indexCssSha256": "64位hex", "cssVars": {} },
  "pages": [], "fixtures": [] }
```

- `indexCssBytes` / `indexCssGzipBytes` 必须是正数，`indexCssSha256` 必须是 64 位 hex；任一不合法 → `exit 1` 并打印具体字段名（第 59–72 行）。baseline 已存在但结构坏了属于配置错误，不能静默跳过。
- 字段名与 P1-6 的约定不一致时，CI 会直接红并指出缺哪个字段——这是首轮上线要核对的点（见 §5.2）。

### 2.2 比什么、阈值多少

找到 `examples/blog/dist/index.html` 里 `<link rel="stylesheet" href="...">` 引用的本地样式表（解析规则见 2.3），把文件字节拼起来得到 `cssBuffer`，计算三个值：

| 指标 | 计算方式 | 判定 |
| --- | --- | --- |
| 字节数 | `cssBuffer.length` | 与 `baseline.css.indexCssBytes` 的相对误差 ≤ **±5%**（`BYTE_TOLERANCE = 0.05`，第 35 行）。PLAN §P1-5 验收标准就是「字节数与上游 `index.css` 差异 ≤5%」 |
| gzip 体积 | `zlib.gzipSync(cssBuffer, { level: 9 }).length` | 与 `baseline.css.indexCssGzipBytes` 的相对误差 ≤ **±5%**（`GZIP_TOLERANCE = 0.05`，第 36 行）。baseline 的 gzip 由 P1-6 用什么压缩器/级别生成未定，±5% 用来吸收 level 6 与 level 9 的差异。本机实测（`node -e`）：2.2 KB 样本 level 6 = 524 B、level 9 = 524 B（差 0.000%）；302,840 B 合成 CSS level 6 = 2361 B、level 9 = 2361 B（差 0.000%）。合成 CSS 重复度高，真实上游 CSS 的差值会略大，但仍远小于 5% |
| SHA-256 | `crypto.createHash('sha256').update(cssBuffer).digest('hex')` | 与 `indexCssSha256` 比较，**只记录不判失败**（第 146–150 行打印 `WARN`）。原因：迁移期的验收标准是 ≤5% 字节差异，不是逐字节一致；SHA 硬失败会让 P1-5 按标准通过时 CI 仍然红。等字节级收敛后把这一段改成硬失败即可 |

任一字节/gzip 超阈值 → 打印 `[verify-css] FAIL <指标>: 实际 X / baseline Y（±Z%，阈值 ±5%）`，末尾 `[verify-css] 比对失败`，`exit 1`（第 152–155 行）。
全部通过 → 打印 `[verify-css] 比对通过`，`exit 0`（第 156 行）。

### 2.3 怎么选 CSS 文件（与上游 `index.css` 的映射）

1. 读 `dist/index.html`，抓 `<link>` 标签里 `rel` 含 `stylesheet` 的 `href`（第 87–92 行）。
2. 没有外部样式表 → `exit 1`，输出 `index.html 没有引用外部样式表：P1-5 要求构建产出独立 CSS 文件`（第 94 行）。这条针对当前 823 字节 inline 产物：P1-5 的验收要求就是「产出独立 CSS 文件」，inline 状态必须红。
3. 一个样式表 → 直接比该文件；多个 → 按文档顺序拼接后比对，并逐个打印文件（第 116–121 行）。上游 baseline 是整个 `public/css/index.css` 单文件，拼接是「index 页面实际生效的全部 CSS」的等价近似。
4. 路径按 `DIST_DIR` 解析：去掉 query/hash、剥掉开头 `/`、做目录越界检查（第 98–114 行）；外链（`http(s)://`）→ 直接失败；href 指向的文件不存在 → 失败并打印缺失路径。

### 2.4 baseline 缺失时的行为

`if (!existsSync(BASELINE_PATH)) { log('baseline 未就绪，跳过比对'); process.exit(0) }`（第 44–47 行）。

- 不读 dist、不报错、**退出码 0**，CI 变绿。
- 原因：baseline 由 P1-6 并行产出，CI 不能因为它的产出还没进仓库而红。
- 跳过时会打印唯一一行 `[verify-css] baseline 未就绪，跳过比对`，CI 日志里可直接搜这行区分「真跳过了」和「静默没跑」。

### 2.5 其他行为

| 场景 | 行为 | 退出码 |
| --- | --- | --- |
| baseline 不存在 | 打印 `baseline 未就绪，跳过比对` | 0 |
| baseline 存在但 JSON 非法 | `FAIL 读取 baseline 失败（<路径>）：<解析错误>` | 1 |
| baseline 缺 `css.*` 字段 | `FAIL baseline.css.<字段> 缺失或非法` | 1 |
| baseline 就绪、dist/index.html 不存在 | `FAIL 构建产物缺少 .../index.html，先跑 pnpm --filter blog build` | 1 |
| 字节数或 gzip 超 ±5% | `FAIL <指标>: 实际 X / baseline Y（±Z%，阈值 ±5%）` | 1 |
| 只有 SHA 不一致 | `WARN SHA256 不一致（记录，不判失败）` + `比对通过` | 0 |
| 全部命中 | `PASS` 三行 + `比对通过` | 0 |

## 5. GitHub 上线还缺什么

### 5.1 已具备（实测）

| 项 | 实测证据 |
| --- | --- |
| 远程仓库存在、默认分支 `main`、公开 | `gh api repos/mcxiaochenn/astro-theme-anzhiyu` → `full_name=mcxiaochenn/astro-theme-anzhiyu`、`private=False`、`default_branch=main`、`visibility=public`；`.git/config` 里 `[remote "origin"] url = https://github.com/mcxiaochenn/astro-theme-anzhiyu.git`，`.git/HEAD` 为 `ref: refs/heads/main` |
| Actions 已启用 | `gh api repos/mcxiaochenn/astro-theme-anzhiyu/actions/permissions` → `{"enabled":true,"allowed_actions":"all","sha_pinning_required":false}` |
| 不要求 action 固定到 SHA | 同上 `sha_pinning_required: false`，所以 `@v4` 这类 major tag 可被仓库策略接受；若后续开启 SHA pinning，需要把三个 action 改成 40 位 commit SHA |
| Registry 无冲突 | `.npmrc` 只有 `node-linker=hoisted`（读自 `.npmrc`），`pnpm-lock.yaml` 里 `npmmirror|registry` 匹配数为 `0`（`Select-String` 输出 `(count) 0`），CI 默认走官方 registry，无私有包 |
| 版本匹配 | 本地 `pnpm --version` → `10.29.3` 与根 `package.json` 第 5 行 `packageManager@10.29.3` 一致；CI 省略 `version` 后安装同一版本。`astro@7.4.13` 的 `engines.node` 是 `>=22.23.4`，CI Node 24 满足 |
| 不会被 gitignore 吞掉 | `.gitignore` 只忽略 `dist/`、`.output/`、`.astro/`、`node_modules/`、日志、`.env*`、OS/编辑器文件，没有匹配 `.github/`、`scripts/`、`docs/` 的规则，新文件正常入库 |

### 5.2 缺的 / 需要人为确认的

| # | 事项 | 现状 | 谁来做 |
| --- | --- | --- | --- |
| 1 | 三个产出必须**同一个 commit** 一起提交 | `.github/`、`scripts/`、`package.json` 的 `verify` 脚本互相依赖：只推 `ci.yml` 时第 6 步 `pnpm verify` 会因脚本缺失失败 | 组长提交时 |
| 2 | `docs/reference/baseline.json` 还没进仓库 | `Test-Path docs\baseline.json` → `False`。第一次 CI 会绿，但 verify 走的是跳过分支，**CSS 比对没有真正执行** | P1-6 完成后提交 |
| 3 | baseline 字段名必须与脚本约定完全一致 | verify 只认 `css.indexCssBytes` / `css.indexCssGzipBytes` / `css.indexCssSha256`；不一致 → `exit 1` 并报 `baseline.css.<字段> 缺失或非法` | baseline 落地后对一眼 |

## 7. 已知限制

1. **SHA-256 不判失败**（§2.2）。这是为符合 P1-5「≤5% 字节差异」的验收标准做的取舍；基线负责人若要求字节级一致，改 `verify-css.mjs` 第 146–150 行即可。
2. **多 stylesheet 拼接是近似映射**。上游 baseline 是单个 `public/css/index.css`；若 Astro 侧把样式拆成多个文件，拼接后的字节数可比、SHA 必然不同（已按 WARN 处理）。P1-5 完成后如果产物是单文件，这条限制不触发。
3. **gzip 生成方式未对齐**。本脚本用 Node zlib level 9；P1-6 若用 `gzip -9` 或 Python 产生 baseline，差值应远小于 5%，但第一次真实比对时以日志里的实际百分比为准。
4. **baseline 字段名是唯一约定的硬契约**。P1-6 若把字段名改成 `cssBytes` 之类，CI 会红并明确报字段名，属于预期行为而不是脚本 bug。
5. **`node_modules/yaml` 是 Astro 的传递依赖**（lockfile 里 `astro 7.4.13(stylus@0.64.0)(yaml@2.9.1)`），只被我本地的 YAML 校验脚本借用，**流水线本身不依赖它**；`verify-css.mjs` 只用 Node 内置模块（`node:crypto` / `node:fs` / `node:path` / `node:url` / `node:zlib`）。
